# Optimize v1.1 Globalization Design

## Status and scope

This design extends approved Optimize v1 at `e86b358aaa67250fc80a32864fb387fa9598ea14`. It does not replace the L0/L1/L2/L3 model, weaken Git-backed evidence, rewrite v1 review artifacts, modify Teaching AI, or install global files during development.

The release goal is one low-friction Codex context policy that remains almost invisible for small work and activates durable repository state only when persistent operational memory has clear value.

## Invariants inherited from v1

- Exact repository and external authority outranks durable operational state; conversation memory remains lowest authority.
- State cannot override source, tests, contracts, approved decisions, Git, or original reviewer evidence.
- Git branch, exact commit identity, ancestry, state-only descendants, worktree drift, regular blob modes, HEAD/index identity, symlink protection, and checkout-filter-independent evidence remain enforced.
- Complete tests and independent review are correctness gates, never token-saving targets.
- Recovery begins with bounded navigation and escalates to broader reads only when exact evidence requires it.
- Agent phases use one bounded long wait and never routine short polling or liveness-only status calls.
- Audit chronology stays outside the default current-state recovery path.

## Approaches considered

### Replace v1 with a generic schema

This produces a superficially clean implementation but invalidates existing v1 state, fixtures, commands, and Teaching AI rollout material. It is rejected.

### Keep milestone fields and add optional aliases

This minimizes code changes but leaves ambiguous dual fields such as `milestone` plus `work_id`, and generic repositories still inherit Teaching AI document assumptions. It is rejected.

### Versioned compatibility with explicit migration

This is the selected approach. The validator continues to accept schema version 1 unchanged and adds schema version 2 for generic state. New initialization creates only v2. Migration is explicit, deterministic, Git-reversible, and validated. Legacy templates remain available while generic templates live beside them.

## Operating modes

### Lightweight

Lightweight mode applies targeted reads, progressive diff/document loading, bounded output, exact verification, and the no-short-polling rule. It creates no `.agent` files and runs no state validator merely because the global skill exists.

Choose it when work is clearly small, single-session, single-agent, narrowly scoped, and unlikely to require compaction or handoff. When uncertain, start lightweight.

### Stateful

Stateful mode uses L0/L1/L2/optional L3, checkpoints, validation, scoped packets, recovery, and durable work-unit boundaries. Any clear multi-agent, independent-review, resumable, multi-phase, long-running, planned, or compaction-risk condition justifies it.

One durable stateful work unit normally maps to one root task. Lightweight tasks do not create artificial root boundaries.

### Upgrade

Lightweight may upgrade to stateful at any time. The upgrade initializes L1, reconstructs current work from Git and exact L0, writes L2, optionally writes L3, stages L1/L2, validates, and then continues. Automatic stateful-to-lightweight downgrade is outside v1.1.

## Generic work unit

Schema v2 replaces the milestone business field with two non-empty strings:

```toml
version = 2
work_type = "feature"
work_id = "factor-engine"
status = "IMPLEMENTING"
branch = "feat/factor-engine"
baseline = "<exact-commit>"
head = "<verified-work-commit>"
owner = "root" # optional
```

`work_type` is intentionally open rather than enum-constrained. `work_id` is an opaque project identifier. `owner` is optional; it becomes useful when responsibility is delegated. Status retains v1's small workflow vocabulary because those values describe state transitions rather than Teaching AI taxonomy.

The v2 L2 sections are `Constraints and clarifications`, `Completed`, `Remaining`, `Open findings`, `Last verification`, `Next action`, `Do not`, and `Authority`. The 12 KiB limit and verified-work HEAD semantics remain unchanged.

## Generic authority and project map

Schema v2 project-map front matter is:

```toml
version = 2
current_state_path = ".agent/current-work.md"
active_state_path = ".agent/active.md"
authority_paths = []
```

`authority_paths` is a required list that may contain zero, one, or many repository-relative files. Each entry receives the same containment, HEAD/index, regular-mode, and symlink checks as v1 spec/plan/audit paths. Empty authority is valid because source, tests, and Git remain L0 without manufactured documents.

The v2 L1 sections are `Authority`, `Code map`, `Verification`, `Important interfaces and contracts`, and `Operational state`. Optimize does not prescribe code areas. The 8 KiB budget remains.

## Generic active state

Schema v2 L3 uses required `version = 2` and `action`, with optional `owner`. Its sections remain `Why`, `Do not`, `On success`, and `On failure`. It stays ignored, disposable, and bounded to 4 KiB.

## Compatibility and path selection

- Existing explicit v1 `--map`, `--state`, and `--active` invocations continue to work.
- With no `--state`, `validate` prefers `.agent/current-work.md`; if absent, it falls back to `.agent/current-milestone.md`.
- Document version selects the exact closed schema; mixed v1/v2 map-state pairs fail clearly.
- Existing root v1 templates remain unchanged. New templates are stored under `templates/generic/`.
- Existing v1 behavioral evidence and tests continue to pass without rewriting their historical artifacts.

## Migration

`migrate --repo <path>` performs a preflight before writing:

1. require a Git repository and a clean tracked/index state;
2. require valid v1 map/state and no existing `.agent/current-work.md`;
3. preserve branch, baseline, verified head, status, completed work, remaining work, findings, verification, next action, prohibitions, and authority content;
4. convert `milestone` to `work_type = "milestone"` and `work_id`;
5. convert `current_agent` to optional `owner` to preserve responsibility;
6. convert spec/plan/audit paths to ordered unique `authority_paths`;
7. rename only generic headings and state pointers;
8. move `current-milestone.md` to `current-work.md` and convert L3 when present;
9. validate the resulting v2 state once L1/L2 are staged;
10. print exact `git restore`/cleanup rollback instructions and never commit automatically.

`--dry-run` reports the deterministic changes without writing. Re-running after migration validates/reports the existing v2 state. Migration never edits business code, contracts, or audit history.

## Per-repository initialization

`init --repo <path> --work-type <type> --work-id <id> [--owner <owner>]` is only for stateful work. It:

- resolves the Git root and exact branch/HEAD;
- refuses v1 state with a migration diagnostic;
- refuses partial/colliding state instead of overwriting it;
- creates generic L1/L2 and appends exactly one `.agent/active.md` ignore line;
- leaves authority and code taxonomy empty with concise fill-in comments;
- never guesses spec, plan, audit, architecture areas, or verification commands;
- does not edit repository AGENTS automatically;
- is idempotent when the same valid v2 state already exists;
- tells the caller to fill navigation, stage L1/L2, and run validation.

Writes are preflighted and use temporary files plus atomic replacement where practical.

## Global installation

Official discovery on 2026-09-14 establishes:

- user skills: `$HOME/.agents/skills`;
- global instructions: `$CODEX_HOME/AGENTS.md`, defaulting to `$HOME/.codex/AGENTS.md`;
- a non-empty `$CODEX_HOME/AGENTS.override.md` is the active global file instead.

`install-global` detects `HOME` through `Path.home()` and `CODEX_HOME` through the environment, with explicit test-only/path override flags. It installs only:

1. `$HOME/.agents/skills/context-state-management`;
2. one bounded marker block in the active global AGENTS file;
3. `$CODEX_HOME/.optimize-context-install.json` describing the managed skill digest and exact managed router segment.

The router selects lightweight versus stateful behavior and delegates details to the skill. It does not copy the skill body.

An existing unmanaged skill, unknown install-state file, duplicate/damaged marker, modified managed skill, or inconsistent managed segment causes a nonzero conflict without mutation. An unchanged same-version install is a no-op. An unchanged Optimize-managed older version may be atomically updated. No config.toml value is changed.

`uninstall-global` removes only the exact managed skill directory, exact recorded router segment, and install-state file. Other skills and all non-Optimize AGENTS bytes are preserved. A modified managed skill or router fails safely for manual reconciliation.

Development and release verification use temporary homes. The real user home is not changed until the controlled rollout reaches its final stage.

## Implementation boundaries

- `scripts/optimize_context.py` remains the compatible CLI and state/evidence validator.
- `scripts/optimize_global.py` owns global path discovery, marker/state management, tree digests, install, and uninstall.
- `templates/generic/` contains v2 map, current-work, and active templates.
- `templates/work-metrics.json` provides generic metric names while the v1 milestone fixture remains supported.
- `tests/test_globalization.py` owns generic schemas, modes-as-policy, init, migration, global install, and compatibility attacks.
- Existing v1 files and tests stay in place.

No daemon, scheduler, database, background service, task classifier framework, opaque memory, or second authority store is introduced.

## Verification strategy

Automated fixtures cover Teaching-AI-like v1, generic Python without spec/plan/audit, lightweight no-state behavior, feature and issue work units, existing global AGENTS, unrelated skills, and v1 migration. Attack tests cover path traversal, symlinks, stage/HEAD divergence, partial init, unmanaged/modified skills, marker corruption, idempotency, uninstall restoration, custom CODEX_HOME, and autocrlf clones.

Fresh-context behavioral tests cover lightweight selection, stateful selection, lightweight upgrade, generic recovery without formal documents, Teaching-AI-like migration, new-root recovery, install/uninstall preservation, idempotent install, reviewer independence, and bounded waiting.

Final review uses a new context and must find no Critical or Important blocker. The reviewer explicitly checks v1 regression, over-triggering, under-triggering, installation safety, instruction conflicts, migration loss, authority weakening, state bureaucracy, and Teaching AI compatibility.

## Controlled rollout

v1.1 produces a plan rather than modifying the real global installation:

1. Teaching AI exercises stateful migration/adoption.
2. A structurally different project exercises generic stateful work.
3. Several small tasks exercise lightweight behavior with no `.agent` files.
4. Only after measured regression review may the user run real global installation.

## Architecture self-review

- No `TBD`, optional semantic ambiguity, or silent migration exists.
- v1 schema and historical evidence remain intact.
- v2 is smaller than a general project-management schema and retains the same state budgets.
- Global writes are bounded, owned, idempotent, reversible, and conflict-sensitive.
- Simple work pays only the global skill description/router cost and creates zero persistent repository state.
- All user success criteria map to an implementation task and test family.
